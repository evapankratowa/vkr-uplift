# Внешние зависимости и их контракты

Система определения сегментов коммуникации работает в контуре банка и стыкуется
с тремя внешними системами. В публичный репозиторий они **не входят**
(проприетарные или требующие лицензий), но их контракты зафиксированы здесь,
а в коде изолированы за адаптерами — это позволяет развернуть и проверить всю
внутреннюю логику без них.

## 1. Apache Zeppelin — аналитический контур

**Роль:** среда исполнения исследовательских ноутбуков (профиль данных,
сравнение архитектур, отчёты для аналитиков). В терминах IDEF0 — механизм.

**Контракт:** ноутбуки читают выгрузки из `data/` и пишут результаты в
`output/`. Никаких вызовов Zeppelin API из кода нет; заменяемая зависимость —
те же ноутбуки (`notebooks/01..05`) исполняются в Jupyter без изменений.

**Замена в репозитории:** `jupyter` из `requirements.txt`; порядок запуска —
нумерация файлов.

## 2. Результаты A/B-экспериментов — источник обучающих данных

**Роль:** выгрузки завершённых рандомизированных экспериментов (факт отправки
коммуникации, факт отклика) — вход для обучения и валидации uplift-моделей.

**Контракт (вход):** таблица с полями `client_id`, `treatment_flg` (0/1),
`target` (0/1), набор ковариат. Адаптер `src/uplift_system/datasets/open_data.py`
приводит выгрузку к `UpliftDataset`: идентификатор — в `id`, воздействие — в
`treatment`, бинарный отклик — в `outcomes["purchase"]`, ковариаты — в `features`.
Для Hillstrom допустим исходный файл с колонками `segment` и `visit`/`conversion`:
адаптер оставляет выбранную ветку и `No E-Mail`, затем сам строит бинарное
воздействие. Истинный индивидуальный эффект у реальных RCT не заполняется
(`ite_true=None`).

**Замена в репозитории:** открытые RCT — X5 RetailHero (~200 тыс. клиентов,
доля теста 0.5, отклик 0.62) и Hillstrom (64 тыс., три ветки), загружаются
`make data`; плюс синтетический генератор с известным истинным эффектом
(`datasets/synthetic.py`) для проверки против истины.

## 3. Система рассылок — потребитель сегментов

**Роль:** исполнение кампании по сформированному сегменту.

**Контракт (выход):** реализация — `src/uplift_system/segments/export.py`,
команда `make segments`. CLI создаёт оба формата выгрузки, каждый в CSV и Parquet,
в `output/tables/`. Префикс имени равен имени каталога проекта (в Docker — `app`):

- `standard`: `<префикс>_segment_<campaign_id>.<csv|parquet>` — только целевой
  сегмент, по одной строке на клиента. Состав и порядок атрибутов задаёт
  `export.columns` в `configs/campaign.yaml`; отсутствующие в сегменте колонки
  пропускаются. Обязательный идентификатор — `client_id`.
- `ab`: `<префикс>_segment_ab_<campaign_id>.<csv|parquet>` — те же целевые строки
  с `group=target` плюс удерживаемая контрольная группа с `group=control`;
  `group` добавляется последней колонкой. Контроль случайно и воспроизводимо
  выбирается из оценённой аудитории вне сегмента (`seed` из конфига), поэтому
  пересечения по `client_id` нет. Его размер —
  `min(round(N_target * export.control_share), N_available)`. Атрибуты отбора
  контрольной группы не заполняются (в CSV это пустые поля).

**Замена в репозитории:** файловая выгрузка; контрольная группа формируется
внутри системы, поэтому оценка эффекта кампании возможна и без интеграции.

## Почему так

Изоляция внешних систем за файловыми контрактами — осознанное проектное
решение: система остаётся тестируемой и воспроизводимой на открытых данных,
а подключение боевых контуров сводится к замене адаптера, не затрагивая
ядро (модели, метрики, сборщик сегментов).
