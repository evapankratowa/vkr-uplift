# vkr-uplift — система определения сегментов коммуникации на uplift-моделировании

[![CI](https://github.com/USER/REPO/actions/workflows/ci.yml/badge.svg)](https://github.com/USER/REPO/actions/workflows/ci.yml)
<!-- Заглушка: заменить USER/REPO на реальный адрес репозитория после публикации на GitHub. -->

Кодовая часть ВКР «Разработка информационно-аналитической системы определения
сегментов коммуникации для клиентов банка с помощью uplift modeling»
(РАНХиГС, 09.03.03 Прикладная информатика).

**Что делает:** отвечает, каким клиентам отправка коммуникации даёт положительный
прирост отклика (uplift), и собирает под фиксированный бюджет контактов сегмент,
дающий больше инкрементальных откликов, чем отбор по прогнозной модели отклика.

**Для кого:** рецензент — проверяет происхождение результата; аналитик —
переиспользует метод; автор — воспроизводит прогон через месяцы.

**Порог практической значимости:** прирост инкрементальных откликов на топ-30%
аудитории ≥ 10% относительно response-модели; разница между архитектурами
значима при Δ нормированного Qini > 0.01 вне 95% бутстрап-ДИ.

## Ожидаемый результат

Успешный прогон создаёт в `output/` таблицы и графики с префиксом `VKR_uplift_`:
сравнение архитектур по Qini/AUUC (`..._architectures_*.csv`), кривые Qini
(`..._qini_curves_*.png`), сравнение стратегий отбора
(`..._value_by_control_share_*.png`) и CSV сегмента для рассылки.
Контрольные числа для сверки — в [docs/DATA_PASSPORT.md](docs/DATA_PASSPORT.md)
(раздел «Контрольные числа»: 50 000 строк, доля отклика 0,4795,
X5 — 200 039 строк с долей теста 0,50 и др.).

## Quick Start

```bash
# Вариант 1: Docker (нужен только Docker)
docker compose up --build        # поднимет PostgreSQL 16 и прогонит весь пайплайн
# проверка БД с хоста (порт 5433: на 5432 часто сидит локальный postgres):
psql -h localhost -p 5433 -U uplift -d uplift -c '\dn'   # схемы: uplift, uplift_dw
# сверка контейнерного прогона с золотыми эталонами (tests/golden/, допуск 1e-6):
docker compose run --rm app pytest tests/test_golden.py

# Вариант 2: локально (нужен Python 3.11)
make install                     # venv + зависимости + пакет в режиме разработки
make test                        # 111 тестов, данных и сети не требуют
make all                         # simulate → train → evaluate → economics → segments → checks

# опционально, нужна прямая сеть (хосты открытых датасетов):
make data                        # скачать открытые RCT (X5, Hillstrom) в data/raw
```

Команды выполняются по порядку в чистом клоне без устных дополнений автора.
`make data` **опционален** и в `make all` не входит: без него пайплайн честно
предупреждает и подставляет синтетические ковариаты (fallback, seed в `configs/`),
а связанные проверки в `make checks` получают жёлтый вердикт «нет входа», а не
падают. Выгрузку кэшбэка (учебный набор DANO/НИУ ВШЭ) при наличии кладут в
`data/raw/` руками — см. раздел «Входные и выходные данные».

## Требования

- Python **3.11** (собрано и проверено на 3.11.5) или Docker;
- PostgreSQL 16 — только если нужен слой БД (в Docker поднимается сам);
- прямая сеть — только для опционального `make data`.

Зависимости: [requirements.txt](requirements.txt), пакет — `src/uplift_system`
(`pip install -e .`, консольная команда `uplift`).

## Порядок воспроизведения

Единая точка входа — `make all`. По этапам:

| Этап | Команда | Что делает |
|---|---|---|
| 1. Данные (опционально) | `make data` | скачивает открытые RCT в `data/raw/`; без него — синтетический fallback |
| 2. БД | `docker compose up db` | применяет `db/001_init.sql` (схемы `uplift`, `uplift_dw`); с хоста БД на порту **5433** (`psql -p 5433`) |
| 3. Симуляция A/B | `make simulate` | размер выборки, MDE, рандомизация, A/A, оценка ATE |
| 4. Модели | `make train` | S-, T-, X-learner, класс-трансформация; DR-, R-learner, Causal Forest |
| 5. Оценка | `make evaluate` | Qini, AUUC, uplift@k; PEHE/Kendall на синтетике; ценность стратегии |
| 6. Экономика | `make economics` | ценность кампании по каналам: три сценария цены SMS, бутстрап-ДИ |
| 7. Сегмент | `make segments` | отбор под бюджет, проверка ограничений, выгрузка CSV/Parquet |
| 8. Проверки | `make checks` | отчёт проверок в `checks/` |

`make all` — это этапы 3–8 целиком: `simulate → train → evaluate →
economics → segments → checks`.

Ноутбуки идут в том же порядке: `notebooks/01` профиль данных → `02` симулятор
и дизайн → `03` сравнение архитектур → `04` оценка стратегий → `05` демо
сегмента. В `03` параметры `N_CLIENTS=20000`, `REPEATS=2` — проверочный прогон
5–7 минут; `50000` и `5` — полный, 30–40 минут.

## Входные и выходные данные

**Входы:**

| Данные | Источник | Как получить |
|---|---|---|
| Синтетика с известным эффектом | генератор `datasets/synthetic.py` | создаётся прогоном, seed в `configs/` |
| X5 RetailHero (реальный RCT, SMS) | [ods.ai/competitions/x5-retailhero-uplift-modeling](https://ods.ai/competitions/x5-retailhero-uplift-modeling) | `make data` |
| Hillstrom (реальный RCT, e-mail) | [MineThatData, 2008](https://blog.minethatdata.com/2008/03/minethatdata-e-mail-analytics-and-data.html) | `make data` |
| Выгрузка кэшбэк-программы банка, 50 000 клиентов, 2022 | учебный набор НИУ ВШЭ, проект DANO | [описание и получение](https://dano.hse.ru/mirror/pubs/share/796520525); положить в `data/raw/cashback_raw_2022-11-15.csv` |

Все данные открытые или синтетические; реальные банковские данные не
используются, персональных данных нет. Происхождение, окна наблюдения,
известные дефекты и контрольные числа каждого источника —
[docs/DATA_PASSPORT.md](docs/DATA_PASSPORT.md).

**Выходы:** таблицы метрик (`output/tables/`: сравнение архитектур, сводная
экономика по каналам, выгрузки сегмента), графики (`output/figures/`),
CSV/Parquet сегмента для системы рассылок (форматы `standard` и `ab` —
с удерживаемой контрольной группой), обученные модели (`models_store/`),
отчёт проверок (`checks/`). Воспроизводимость ключевых чисел малого прогона
контролирует `tests/test_golden.py` против эталонов `tests/golden/`.

## Архитектура и внешние зависимости

Схема системы (компоненты, развёртывание, модель данных) —
[docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Три внешние зависимости осознанно **не входят** в репозиторий и подключаются

## Структура

```
├── db/001_init.sql      DDL PostgreSQL 16: схемы uplift и uplift_dw
├── configs/             параметры DGP, дизайна эксперимента, моделей, кампании (seed зафиксирован)
├── src/uplift_system/   пакет: datasets, experiment, models, evaluation, segments, checks
├── notebooks/           демонстрация по порядку 01 → 05
├── tests/               111 тестов (6 пропусков без PostgreSQL — pytest.mark.docker;
│                        золотые эталоны end-to-end — tests/golden/)
├── docs/                паспорт данных, архитектура, внешние контракты, источники
├── data/                raw/interim/processed (скачиваются, в репозитории не хранятся)
├── output/              таблицы и графики результата (пересоздаются прогоном)
├── models_store/        обученные модели joblib + манифест (создаётся make train)
├── checks/              отчёт проверок checks.json + markdown (создаётся make checks)
├── Dockerfile, docker-compose.yml   развёртывание без внешних зависимостей
└── Makefile             единая точка входа: make all
```
